# 复制诊断信息与本机同步记录

## 依据

一键诊断方案修订二的 1b 和「默认在本机保留最近 10 次同步摘要」。两项都在架构审批门内，维护者 Hogan 于 2026-11-09 批准，原话「可以开工，你派活吧。 1、2、3我都同意。」批准范围：正式版的「复制诊断信息」只输出最小本机摘要；Claude Code 自己的错误输出第一版不带，只给退出码和固定原因；不做 Vibe 账号标签；App 在本机保留最近 10 次同步摘要。超出这些范围的收集项、上传任何诊断数据，都要重新过审批门。

追加批准：

- 2026-11-11，同步记录新增 `cliFallback`（引导器连不上 npm、改跑本机缓存的 CLI 时记一个固定阶段词），「复制诊断信息」显示为「用了本机缓存的 CLI（…）」。维护者 Hogan 批准，原话「批准」。批准时的说明：只存固定词，不存原文、路径、版本号；只写在本机，不上传；旧记录照常读取；随下一版 Windows 发布；不批可单独撤回。

方案的「2′：两个 App 并入 `doctor --json`，等 CLI 发布后做」也在这次批准的方案里。CLI 0.14.11 起带 `doctor --json`（`schemaVersion: 1`，字段约定见 vibe-usage 仓库 `docs/doctor-json.md`），App 从下一版起并入，字段只取下文「CLI 诊断」一节列出的那些。

测试构建的 `test_diagnostics`（只在 debug 和 `external-test-diagnostics` 构建里编入）保持原样，和本功能互不相干。

## 入口

设置页「关于」分组里的「诊断信息」一行，按钮「复制诊断信息」。点了才收集；收集完复制到剪贴板，提示「已复制，可以直接贴到群里」，旁边「查看全文」可以展开核对。不点就什么都不发生，任何内容都不会自动上传。收集时同时跑一次 CLI 的 `doctor --json`，最多等 30 秒，所以按钮可能显示「收集中…」十几秒。

## 报告里有什么

只放白名单字段：每一项都是枚举、数字、布尔或我们写死的模板。后端 `src-tauri/src/services/diagnostics.rs` 只交出这些结构化字段，前端 `src/lib/diagnostics.ts` 负责排版。

| 字段 | 内容 | 不放 |
|-|-|-|
| 环境 | Windows 10/11、功能更新名（如 `23H2`）、build 号、架构；App 版本和构建类型；运行环境类型（App 内置 Node / 系统 Node / Bun）及版本号 | 路径 |
| CLI | 启动脚本在不在；引导器缓存里最高的完整 CLI 版本；`doctor` 实际运行的 CLI 版本，或它没能回答的固定原因（见下一节） | CLI 输出 |
| 账号 | 是否已配置 Key；只看最新一条同步记录：成功写「未被服务器拒绝」，Key 被拒写「被服务器拒绝（Key 无效）」，其他情况（超时、CLI 没起来、网络失败、服务器错误、其他失败）一律写「无法判断 Key 是否被拒」；不会越过最新一条去找更早的结果，口径与 macOS 和 CLI 一致；4 位设备标签（主机名 SHA-256 的前两个字节） | Key、handle、主机名 |
| 网络 | 系统代理：无 / 本机地址 / 外部地址 / 已开启但无法识别；是否设了自动代理脚本（PAC，「使用设置脚本」，只看有没有 `AutoConfigURL`，不读地址）；有没有传给同步（Claude 配额读取从不传）；`HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY` 是否设在用户变量、系统变量、App 自己的环境里 | 代理地址、端口、账号、密码 |
| 后台 | App 定时同步是否在运行、是否正在同步、上次成功时间 | |
| 最近同步 | App 自己的同步记录（见下一节） | 同步输出原文 |
| 订阅配额 | 每张已开启卡片的状态、1a 的固定原因代码、实际来源、窗口个数、数据新旧（不到 1 小时按分钟，不到 2 天按小时，再往上按天） | 数值以外的任何文字；`Error` 状态的 message |
| Claude 读取明细 | 当前候选程序（固定模板，如 `~\.local\bin\claude.exe`、「PATH 上第 3 个（claude.cmd）→ 包内 claude.exe」）和各自 `--version` 的版本号，单独一节，注明是复制时查的；最近一次真实读取（不写版本：读取时没有记版本，Claude Code 又经常自动更新，不能把现在的版本安到过去的读取上）：桌面端记录用了没有、每个候选 initialize 与 get_usage 的耗时、固定原因、退出码或「被 App 结束」、回答里有没有 `rate_limits_available` / 5h / 7d / 套餐 / error 字段；PATH 上 `claude.*` 的文件名和个数；`ANTHROPIC*` / `CLAUDE*` 用户变量的名字；Claude `settings.json` 里 `env` 的键名；是否设了 `CLAUDE_CONFIG_DIR` | Claude Code 的 stderr 和回答里的值；变量的值；任何目录名 |

变量名只在形如 `[A-Z0-9_]`、不超过 64 个字符时列出，最多 20 个；其余只报个数。版本号只保留数字和点。`--version` 只在点按钮时运行，每个候选最多 5 秒；刷新配额时从不运行。

## CLI 诊断（`doctor --json`，方案 2′）

后端 `src-tauri/src/services/cli_doctor.rs` 用和同步相同的运行环境、目录、发起方标记和代理运行 `doctor --json`，上限 30 秒，和 App 自己那一半、Claude 候选版本同时收集。

拿到 `schemaVersion: 1` 的结果时，逐个字段按类型和形状读进固定结构，其余字段一律丢掉：

- 运行环境：`doctor` 这次用的 Node 或 Bun 及版本号；SQLite 实际用哪种（内置 `node:sqlite` / 系统 `sqlite3` 命令 / 都没有）。
- 账号：服务器是默认地址还是自定义（不报地址）；`state.json` 是否属于当前 Key。CLI 的 Key 判断和设备标签不取，App 自己已经报了，两个算法不同的标签放在一起只会让人糊涂。
- 网络：Vibe 服务器、npm 源能否连上和耗时，连不上时的固定原因；npm 源是官方还是自定义（不报地址）。
- 后台：CLI 后台服务装没装、什么方式运行，最近一次后台同步的时间和结果。
- 设置：是否上传项目名、额外数据目录个数、Kiki / Magpie 切点设没设。
- CLI 同步记录：最多 10 条，每条时间、发起方、结果、耗时、上传条数、失败类别（服务器错误只带状态码数字）、当次 CLI 版本。没有结束记录的一条，如果它的开始时间落在 App 某次「超时，被 App 结束」的那段时间里，并且是 Windows App 发起的，就写成那次超时；否则写「未记录结束，原因未知」，不猜（方案第七节「两份怎么对上」）。
- 工具：只列检测到的和有问题的。每个工具：检测到没有、额外目录个数、上次解析条数、建索引进度、是否跳过、各类警告的错误码和次数、出错的错误码、被服务端丢弃的条数、累计已上传条数；没有自己解析器的工具写「数据并入 …」。

形状核对：版本号只要数字和点；错误码、枚举只要小写字母、数字和 `_-:`，不认识的新错误码照原样显示（约定要求如此），形状不对的丢掉；工具 id 只要小写字母、数字和 `-`；工具名只要 ASCII 字母、数字、空格和 `.+()-`，不符合就用 id 代替。条数上限：同步记录 10 条、工具 64 个、每个工具 32 种警告。前端排版时再按同样的形状核对一遍。

没拿到结果时，报告照样生成，「CLI」一行只写一个固定原因，不出现 CLI 诊断一节：

| 情况 | 报告里写 |
|-|-|
| 没有运行环境或启动脚本、进程起不来、引导器失败（`vibe-usage launcher:`） | 启动阶段失败（和同步记录同一套细分原因） |
| 30 秒内没结束（App 结束它） | CLI 诊断超时 |
| CLI 早于 `doctor`（stderr 是 `Unknown command: doctor`，比如连不上 npm 时跑的旧缓存） | CLI 较旧，没有诊断命令 |
| `schemaVersion` 不是 1 | CLI 较新 / 较旧，诊断格式不认识（只带版本数字） |
| 退出码 0 但输出不是认得的 JSON | CLI 诊断输出无法识别 |
| 其他非零退出 | CLI 诊断命令失败（退出码） |

CLI 的 stdout 只当 JSON 读，stderr 只拿来匹配上面几个固定开头，都不会原样进报告。

## 脱敏

1. 后端只产生上表的结构化字段，不拼接任何原文。
2. 前端排版时再按形状核对每个字符串字段（版本号、变量名、PATH 文件名、设备标签、功能更新名），形状不对就丢掉，变量名改为计数。
3. 输出前按方案第六节第 9 条再整体扫一遍：盘符路径、UNC 路径、`/Users/`、`/home/` 和编码后的项目目录（`-Users-…`）、任何 URL、`vbu_`、`sk-`（含 `sk-ant-`）、`Bearer ` 后的内容、`eyJ` 开头的 JWT、邮箱、40 位以上的长串，统一替换。正常报告里这些都不会出现，这一步只是兜底。

测试（`tests/diagnostics.test.ts`、`diagnostics.rs` 和 `sync_history.rs` 的单元测试）用合成数据逐条验证：中文用户名、带空格的路径、编码后的项目目录、假 Key、假 `sk-ant-` 串、假邮箱、假 JWT、带账号密码的代理地址，都不会出现在报告和同步记录里。

## App 的本机同步记录

文件：`%APPDATA%\ai.vibecafe.vibe-usage.windows\sync-history.json`（与 `settings.json` 同目录），最多 10 条，新的在前，滚动覆盖。每条：开始时间、发起方式（定时 / 手动）、结果（成功 / 失败 / 超时被 App 结束 / CLI 启动阶段失败）、耗时、固定原因；引导器改跑了缓存版本时，再记一个固定的阶段词 `cliFallback`（连不上 npm 源 / npm 源返回错误 / 新版下载或校验失败 / 新版安装失败），报告里在结果后面写「用了本机缓存的 CLI（…）」。只记这个词，不记提示原文和版本号。

- 超时：120 秒时 App 结束 CLI，CLI 自己来不及写任何东西，所以只有 App 能记录。`sync.log`（App 日志目录 `%LOCALAPPDATA%\ai.vibecafe.vibe-usage.windows\logs\`）以前只在 CLI 正常退出时写，超时那次什么都不留；现在超时也写一行固定内容：时间、`timeout=120s`、引导器缓存里最新的完整 CLI 版本（`newest-cached-cli=…`，一般就是这次跑的版本；这次还在下载新版时被结束、或 `latest` 被改回更旧的版本时不是）。不写 CLI 已经输出的任何内容。
- CLI 启动阶段失败：没有运行环境、进程启动失败，或引导器 `cli-bootstrap.mjs` 自己的工作失败（解析、下载、安装、加载 CLI；stderr 以固定前缀 `vibe-usage launcher:` 开头）。引导器失败再按固定前缀细分为：连不上 npm 源 / npm 源返回错误 / 下载或校验失败 / 安装失败 / 其他。CLI 的 `run()` 已经开始以后抛出的异常是 CLI 自己的失败：引导器像 Node 处理未捕获异常那样原样打印、以退出码 1 结束，不加这个前缀，记成下面的「失败」（#34）。以前这种情况会被误记成「CLI 启动阶段失败（引导器其他错误）」，而 CLI 当时可能已经扫描甚至上传了一部分数据。引导器只有在本机缓存里没有可用版本时才会这样失败；有缓存时它改跑缓存里最新的完整版本，并在 stderr 先写一行 `vibe-usage launcher notice: stage=…`。这时 CLI 真的跑了，按 CLI 自己的结果记成功或失败，另记 `cliFallback`；这行提示在分类和状态栏取错误行之前就被去掉，原文只留在 `sync.log` 里。
- 失败：只按这次运行的最终错误行分类，也就是状态栏本来显示的那一行（CLI 的 `✗ …`），不看前面工具输出的非致命警告（例如 `Cursor usage export skipped (HTTP 429 …)`）。Key 被服务器拒绝：CLI 的固定提示「API Key 无效，请运行 … 重新配置。」（部分上传后前面会加「部分完成（已上传 …）: 」），或旧版的 `Invalid API key` / `UNAUTHORIZED`、HTTP 401/403。服务器错误：失败行里的 HTTP 状态码数字。其余记 CLI 退出码，判断不了 Key。

CLI 的输出只用来匹配固定前缀，从不写入记录。记录不含路径、项目名、Key 和任何原文，写入失败不影响同步本身。「重置配置」时删除这个文件；卸载时勾选删除应用数据也会一起删除。CLI 那份同步记录由 CLI 自己负责（`~/.vibe-usage/sync-history.json`，不在本仓库）。
