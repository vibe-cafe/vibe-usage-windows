# Windows 一键更新

本文说明 App 内更新怎样安装新版本、旧版本怎样过渡、发版前怎样测试，以及出问题时怎样撤回。

**批准记录**：维护者 Hogan 于 2026-11-11 在架构审批门批准本方案（原话「按条件批准」），附带的实现和验收条件见本文各节。批准前，方案先经过两轮对抗审查（GPT-6 Astra xhigh、Claude Fable 5.2 xhigh）。

## 安装方式

安装包由 Tauri 2.11.4 的 NSIS 模板生成（`pnpm-lock.yaml` 锁定 `@tauri-apps/cli` 2.11.4）。模板支持三个参数，`tauri-plugin-updater` 也用同样的参数调用它：

| 参数 | 作用 | 模板位置 |
|---|---|---|
| `/P` | 被动模式：跳过欢迎、目录、完成等页面，只显示进度条，装完自动关闭 | `SkipIfPassive`、`SetAutoClose` |
| `/UPDATE` | 更新模式：直接覆盖安装，不运行旧版的卸载程序；不新建快捷方式，保留开机自启 | `PageLeaveReinstall` 第 318–321 行 |
| `/R` | 装完后重新打开 App（只在被动或静默模式下生效） | `.onInstSuccess` |

**新版 App 内更新**（`src-tauri/src/services/updater.rs`）：点「发现更新」后，App 下载安装包并校验 SHA-256，然后带 `/P /UPDATE /R` 启动安装包，接着退出。被动模式的安装包如果发现 App 还没退完，会自动结束它（模板 `CheckIfAppIsRunning`，结束后等 0.5 秒）。同一时间只允许一次安装：下载期间再点会被后端拒绝，前端按钮也处于不可点状态，显示「正在下载更新…」；失败时按钮显示原因，可以重试。

覆盖安装写入文件时，如果某个文件仍被占用，NSIS 会弹出「无法写入文件：中止/重试/忽略」。点「重试」通常就能继续。点「忽略」会跳过这个文件（通常是 `node.exe`，留着旧版也能用），其余照常装完。点「中止」时，电脑上是新旧文件混在一起的状态：已经写入的文件是新版，其余仍是旧版，旧文件没有被删除，「应用和功能」里登记的还是旧版本号；App 已被安装包结束，不会自动重开。恢复办法是再运行一次安装包（下载过的安装包在 `%TEMP%\VibeUsage-<版本>-Setup.exe`，也可以从 Release 重新下载）。因为登记的仍是旧版本号，钩子会再次接管，按覆盖安装补全。

**旧版 App 和手动运行**（`src-tauri/windows/installer-hooks.nsh`）：0.7.5 及更早版本的 App 启动安装包时不带参数，用户也可能直接双击安装包。这两种情况下，模板默认会显示「已安装」页，默认选项是「安装前卸载」。现在由钩子在向导第一页出现前接管：如果没有任何命令行参数，并且注册表里登记着同一产品的更旧版本，就带上 `/P /UPDATE /R` 重新启动安装包自身，原来那份直接退出。以下情况都退回原来的向导：

- 读不到已装版本，或读不到安装包自身的版本（自身版本取自版本资源 `VIProductVersion`，NSIS 默认把它同时写成文件版本）；
- 比较结果不是「安装包更新」：同版本时向导提供修复或卸载，降级时向导会提示风险；
- 重新启动失败；
- 带了任何参数（`/S`、`/P`、`/UPDATE`、`/NS` 等）；静默安装根本不会执行到这一步。

例外是 `/D=`。NSIS 在钩子运行前就把 `/D=目录` 从命令行里去掉了（NSIS 3.11 `Source/exehead/Main.c` 第 275–277 行），所以只带 `/D=其他目录` 运行时，钩子看到的是「没有参数」，照样接管。重新启动的安装包不带 `/D=`，会装回注册表里登记的原目录。这只在手动用命令行给升级换目录时出现，属于极端情况，不加防御代码。

钩子在模板第 34–36 行就被引入，早于模板第 38–77 行定义的常量和变量，所以钩子函数只用 NSIS 自带的内容：产品名取运行时的 `$(^Name)`（外测包用同一份钩子，产品名是「Vibe Usage Test」），注册表根键用 `SHCTX`（模板的 `.onInit` 已经设成当前用户）。MUI2 在第一次 `MUI_LANGUAGE` 时才插入 `.onGUIInit`，并在第一页出现前调用 `MUI_CUSTOMFUNCTION_GUIINIT`（NSIS 3.11 `Contrib/Modern UI 2/MUI2.nsh` 的 `MUI_INSERT`、`Interface.nsh` 的 `MUI_FUNCTION_GUIINIT`）。

## 为什么以前会弹「无法卸载！」

以前升级时，模板会先运行旧版的 `uninstall.exe`。依据模板第 347–383 行：旧卸载程序的退出码不是 0（1 表示用户取消，这种情况不报错），或者卸载后旧主程序还在，就弹「无法卸载！」（`unableToUninstall`），然后退回「已安装」页。会遇到的情况有：

- **在「正在运行，点确定终止」提示上点了取消**（退出码 2）：卸载还没开始，什么都没删，App 完好。
- **`node\node.exe` 删不掉**（退出码 3010）：旧版 App 或它启动的 Node 还没退完。这时卸载已经执行完，主程序、快捷方式、开机自启和「应用和功能」里的登记都已删掉，只剩 `node` 文件夹等重启后删除。卸载钩子重试约 3 秒后才安排重启删除并返回 3010；3010 只说明钩子认为「需要重启」，不能证明删除登记一定成功。这时取消安装，电脑上只剩半个 App；如果再选一次「安装前卸载」，旧卸载程序已经不在了，会再次报错，只能改选「请勿卸载」继续。
- **旧主程序删不掉**（被占用）：卸载照常往下执行，其余文件、快捷方式和登记可能已删掉一部分，只是主程序还在，所以报错。

升级改为覆盖安装后，旧卸载程序不再运行，下面两个老问题也一起消失：

- 升级会把开机自启关掉：模板卸载时会删除 `HKCU\...\Run` 下的 `Vibe Usage`，这正是 `auto_launch.rs` 写入的值。
- 升级时可能误删设置：卸载确认页有「删除应用程序数据」复选框。

注意：以前升级时已经被关掉的开机自启不会自动恢复。

卸载钩子里的 3010 保留不改。它的作用是：卸载没删干净时，不要接着往同一目录重装，否则重启时删掉的会是新装的文件。

## 残留和长期规则

覆盖安装只写入新文件，不删除旧文件。0.7.3 起安装目录里只有主程序、`cli-bootstrap.mjs`、`node\node.exe` 和 `uninstall.exe`，都是同名覆盖。0.7.2 及更早版本带有内置 CLI 目录 `cli\`，`NSIS_HOOK_POSTINSTALL` 会在 `cli\bin\vibe-usage.js` 和 `cli\package.json` 都存在时删除整个 `cli\`。快捷方式保持原样：用户自己删掉的桌面快捷方式不会被加回来。

**长期规则**：以后删除或改名任何打包资源时，审查都要确认 `NSIS_HOOK_POSTINSTALL` 是否需要清理旧路径，因为覆盖安装不会运行旧卸载程序。

## 候选包

`release.yml` 手动运行时有两种构建类型可选：

- `external-test`（默认）：独立的「Vibe Usage Test」应用，不检查更新，附件名 `windows-installer-external-test`。
- `release-candidate`：和正式版是同一个应用身份，正常检查更新，用来在发版前真机测试升级。文件名为 `VibeUsage-<版本>-Windows-Candidate-<运行号>-Setup.exe`，附件名为 `windows-installer-candidate-<运行号>`，不生成也不上传 `latest.json`。

只有推送 `v*` tag 才会构建正式版并上传到 GitHub Release（`github.event_name == 'push'`）。手动运行即使选的是 tag，也只上传 Actions 附件。

## 撤回

下一版有问题时：

1. 把上一版重新标为 latest，新检查到更新的 App 就会停在上一版；
2. **同时撤下问题版本 Release 里的安装包**。已经显示「发现更新」的 App 缓存了下载地址，要等它下一次检查更新（启动时、之后每 24 小时，或在设置里点「检查更新」）发现没有新版本，才会撤掉提示、忘掉这个地址（#36）；在这之前，第 1 步挡不住它们。这个自动撤掉只对包含 #36 修复的版本有效：0.7.5 及更早的客户端检查到没有新版本时不会撤掉提示，点「发现更新」仍会去下载缓存的地址，只能靠撤下安装包挡住；
3. 再发一版撤回改动。

已装上新版的用户不受影响。即使以后撤掉钩子，新版 App 仍会带 `/UPDATE` 启动安装包，而模板本身就支持这个参数。

## 验收

日常 CI 不打安装包，钩子的语法只有在发布流水线打包时才会被检查。真机验收在 Windows 上用候选包做，测试电脑先装 v0.7.4（它和 0.7.5 的钩子、目录结构都相同）。必须覆盖：

1. App 开着时双击候选包：只出现进度条，App 自动重开；开机自启、设置、登录都还在；
2. 同步进行中升级（0.7.4 基线，面板开着）：如果出现「无法写入文件」，记录下来，等一会儿再测一次；
3. 命令行带 `/P /UPDATE /R` 运行候选包（模拟新版 App 内更新）；
4. 从 0.7.2 升级：`cli\` 被清掉，之后卸载不留文件；
5. 同版本重装、首次安装、降级、`/S` 都不被接管：前三种仍走完整向导，`/S` 仍是静默安装；
6. 装着更低版本的正式版时，首次安装外测包仍走完整向导；
7. 记录是否出现第二次 SmartScreen 提示，以及从点击到出现进度条的时间。

建议在发布前真实点一次新版的「发现更新」：用一个临时分支把清单地址指向本机，再用候选包测试。新版 App 内更新的完整流程，也要在下一版发布后，在装着候选包的电脑上补验一次。

### 2026-11-11 真机结果

用的是 [run #24](https://github.com/vibe-cafe/vibe-usage-windows/actions/runs/43005835167) 的候选包 `VibeUsage-0.7.5-Windows-Candidate-24-Setup.exe`，构建自 `038da96`。之后的提交只改了前端按钮写法、文档和钩子注释，安装行为不变。

测试机是 Windows 11 家庭版。第 1 项由 Hogan 手动做。第 2、3 项通过 SSH 远程执行，安装和启动都放在用户的桌面会话里，以普通权限运行；安装包用 CreateProcess 启动，和 App 内更新的方式相同。

已测，通过：

- **第 1 项**：基线 0.7.4，双击候选包，不带参数。Hogan 看到更新成功。远程复查结果：
  - 开机自启的 Run 项在升级前写入，升级后还在；
  - 设置文件和登录信息都没变；
  - 升级后 3 秒同步成功；
  - Hogan 重启电脑后，App 在登录后约 20 秒启动。这是按启动时间推断的开机自启。
- **第 2 项**：基线 0.7.4，在 App 正在同步、Node 子进程还在运行时，不带参数运行候选包。
  - 原进程 96 毫秒后退出，退出码 0。重新启动的安装包只显示「正在安装」进度页，覆盖 `node.exe` 时没有出现「无法写入文件」。
  - 安装用时约 3 秒，退出码 0。App 自动重开并同步成功，开机自启、设置和登录都保留。
  - 只测了「Node 启动后 0.1 秒内运行安装包」这一种时机。
- **第 3 项**：装着候选包（同为 0.7.5），App 开着，带 `/P /UPDATE /R` 运行候选包。只出现进度页，用时约 3.3 秒，退出码 0。旧 App 在 0.3 秒内被结束，新 App 自动重开，设置保留。
- **第 7 项**：Hogan 从浏览器下载后双击，只弹过一次 SmartScreen。原因是证书不受信任，原来就有。钩子重新启动安装包时没有再弹。App 内更新用 CreateProcess 启动安装包，不会触发 SmartScreen。远程测试中，从启动安装包到出现进度窗口约 0.3 秒。

还没测，**下一版正式发布前要补测**：

- 第 4 项：从 0.7.2 升级后 `cli\` 被清掉，之后卸载不留文件。
- 第 5 项：同版本重装、首次安装、降级都不被接管，仍走完整向导；`/S` 仍是静默安装。
- 第 6 项：外测包隔离。装着正式版时，首次安装外测包仍走完整向导，和正式版互不影响。
